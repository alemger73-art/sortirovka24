# Автоматическая обработка заявок С24

Подготовлено в `codex/s24-crm-telegram-20261012` от `main` (`26c6e4de`).
Запуск на рабочем сайте, новые доступы, миграция рабочей базы и выдача прав
Google/Telegram требуют отдельного согласования владельца. Автозапуска нет.

## Что делает первая версия

Новая заявка и задание доставки сохраняются одной транзакцией:
- `master_requests`: услуги, включая обращения к Автопрофи (сохраняется `master_id`);
- `become_master_requests`: заявки мастеров;
- `business_partner_requests`: заявки партнёров;
- `feedback_requests`: сообщения «не работает сайт», ранее не сохранявшиеся в базе.

Отдельный процесс каждые 5 секунд обрабатывает до 100 этапов доставки:
база → выделенный лист Google Таблиц → Telegram соответствующей категории.
Обычные прямые уведомления этих форм подавляются только при `S24_CRM_ENABLED=true`.
Прочие уведомления сайта, DAM ALEM/оплаты/курьеры не меняются.

Это приём и маршрутизация новых обращений. Решения, звонки, публикации и изменение
статуса заявки выполняет оператор. Двустороннего изменения базы через Google
Таблицы и автоматического переноса старых заявок в этой версии нет.
Снимок содержит статус сайта на момент создания; последующие изменения не синхронизируются.

## CRM и надёжность

Лист `S24_Inbox`: A:N — ID С24, источник, дата, имя, телефон, WhatsApp,
категория, описание, адрес, статус сайта, исполнитель ID, ссылка звонка,
WhatsApp, поиск адреса в 2ГИС. Телефон/WhatsApp доступны ссылками; ссылки поиска
адреса не означают проверку точного здания. С O можно вести статус CRM,
ответственного, следующий контакт и заметку: worker эти столбцы не изменяет.

Для задания № N зарезервирована строка N+1. Повторная запись после таймаута
использует ту же строку; новые строки через append не создаются. Ввод RAW не
исполняет пользовательский текст как формулы. Worker проверяет ID в колонке A
и отказывает при переносе строки или занятой чужой строке.

Лист должен быть выделенным, пустым до инициализации, с достаточным числом строк.
Не сортировать, не удалять/вставлять строки и не редактировать A:N. Для представлений
использовать отдельный лист с QUERY/FILTER. Сбой проверки/недостаточная ёмкость
листа уходит в повторные попытки, а затем в очередь ошибок.
Не менять таблицу/имя листа при существующей очереди: контроль доставки привязан
к этой паре. Новая таблица требует отдельного согласованного переноса истории.

Этап Google фиксируется перед отправкой Telegram. Сбой Telegram не создаёт
повторную строку CRM. PostgreSQL `FOR UPDATE SKIP LOCKED` исключает одновременную
обработку одного этапа несколькими worker. После 10 неудач этап останавливается;
повторы с задержкой 30 секунд → до 1 часа. Текст ошибки и секреты не сохраняются,
только название типа исключения. ID одинаков для повторных уведомлений.

Telegram имеет семантику «как минимум один раз»: если сообщение принято, но ответ
потерян или процесс упал до фиксации результата, повтор может отправить второе
сообщение с тем же ID. Гарантировать отсутствие такого дубля через sendMessage нельзя.

## Доступы и порядок запуска — только после согласования

1. Утвердить конкретную Google Таблицу, отдельный лист, категории/чаты Telegram,
   кто читает контакты и срок хранения. Использовать существующие маршруты Telegram
   при возможности; новый бот/чат подключать только после одобрения.
2. Согласовать Google service account, включение Sheets API и выдачу роли редактора
   только целевой таблицы. Доменное делегирование не требуется. JSON ключа хранить
   в секретах сервера; в репозитории только `.env.crm.example` с пустыми значениями.
3. Проверить копию рабочей БД, применить Alembic на копии, проверить миграцию с
   `dam20261006_pwa_preferences` до `s2420261012_crm_delivery`. Проверить новую заявку
   и сообщение об ошибке. Никаких миграций рабочей базы на этапе подготовки.
4. На согласованном тестовом контуре с отдельной БД/таблицей/ботом проверить полный
   путь и отключение. Общий `EXTERNAL_SIDE_EFFECTS=disabled` блокирует отправку даже
   при двух CRM-флагах. Новые credentials в staging согласовать отдельно.
5. После отдельного разрешения рабочего запуска: применить миграцию, настроить
   секреты и `S24_CRM_ENABLED=true` сначала при `S24_CRM_SEND_ENABLED=false`.
   Новые заявки попадают в очередь. Флаги сайта и worker должны совпадать.
6. После разрешения отправки установить `S24_CRM_SEND_ENABLED=true`, подготовить
   пустой лист с запасом строк, выполнить `--init-header`, затем `--once` с одной
   тестовой заявкой. После проверки запустить worker под supervisor с автоматическим
   перезапуском. Worker не запускается из FastAPI/start.sh.

Из `app/backend` (команды ниже НЕ выполнены на рабочем сервере):

```sh
python -m alembic upgrade head
python scripts/crm_worker.py --init-header
python scripts/crm_worker.py --once
python scripts/crm_worker.py
python scripts/crm_worker.py --status
python scripts/crm_worker.py --retry-id 123
```

`--status` читает только агрегаты без контактов. `--retry-id` сбрасывает ошибки
конкретного задания и сохраняет успешный этап Google. Отправка после сброса
пойдёт в следующем цикле worker. Мониторить процесс, число `dead=true`, число
незавершённых заданий и рост очереди; автоматического отдельного аварийного
оповещения в этой версии нет. Исключение БД завершает процесс с безопасным
сообщением; supervisor должен перезапустить его.

Остановить отправки: `S24_CRM_SEND_ENABLED=false` на worker и остановить процесс;
очередь продолжает накапливаться при включённом capture на сайте. Для возврата
старых прямых уведомлений выключить `S24_CRM_ENABLED` на сайте после остановки
worker. Уже захваченные задания сохраняются; их последующая отправка согласуется.
Миграцию назад не откатывать: история заявок/доставки сохраняется.

## Проверки

```sh
cd app/backend
EXTERNAL_SIDE_EFFECTS=disabled S24_CRM_ENABLED=false python -m pytest -q \
  tests/test_s24_crm_delivery.py tests/test_s24_crm_postgres.py \
  tests/test_migration_upgrade.py tests/test_deploy_safety.py
```

Offline тесты используют локальный SQLite и MockTransport, проверяют атомарность,
порядок, перезапуск, повторы, остановку после 10 ошибок, выключатели, маршруты,
RAW-ввод, защиту занятой/перемещённой строки и новую миграцию.
PostgreSQL тест допускает только localhost/127.0.0.1 и БД `s24_crm_test`, создаёт
уникальную временную схему и проверяет параллельных потребителей. Workflow
`s24-crm-tests.yml` поднимает отдельный PostgreSQL 16 без рабочих доступов.

API: [Google Sheets values.update](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/update),
[service accounts](https://developers.google.com/identity/protocols/oauth2/service-account),
[Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage).
