# Исправления аудита DAM ALEM — 19 сентября 2026

## Заказы и деньги

- Списание, возврат и начисление бонусов используют блокировку пользователя, атомарное изменение баланса и журнал операции. Повтор одного события не меняет баланс повторно. Бонус за заказ начисляется при завершении и подтверждённой оплате, в транзакции заказа.
- Клиентская витрина отправляет постоянный ключ попытки оформления. Повтор с тем же составом возвращает существующий заказ; изменение данных с тем же ключом отклоняется. Старые приложения без ключа совместимы, но этой защитой не пользуются: их необходимо обновить.
- При изменении чека полученная оплата сохраняется отдельно. Поступления, доплаты и возвраты записываются в журнал заказа; отчёт использует даты денежных операций. Для исторических оплат без даты дата не выдумывается.
- Владелец может отметить уже выполненный возврат переплаты после изменения чека, а также остатка оплаты после отмены. Кнопка не переводит деньги через банк.
- Новые заказы сохраняют условия расчёта. При редактировании пересчитываются сервисный сбор, порог бесплатной доставки и скидка. Бонусы дополнительно не списываются. У старых заказов без детализации сохраняется согласованная разница между стоимостью блюд и итогом: автоматически восстановить её состав нельзя.
- Дополнительные порции существующей строки проверяются по стоп-листу; цена старой строки сохраняется. Отсутствующий ресторан, неизвестный способ получения и товары без положительной цены отклоняются.

## Подарки и витрина

Стандартная акция: от 11 000 ₸ стоимости блюд клиент выбирает один десерт — сладкую вату или вафли с фруктами и шоколадом. Подарки связаны с товарами и учитывают их доступность. Владелец может поменять выбор в редакторе подарков. Оператор выбирает подарок при ручном оформлении и при изменении заказа. При уменьшении суммы ниже порога подарок удаляется.

Обновление заменяет только известный прежний стандартный набор подарков. Пользовательские акции и явно очищенный список сохраняются. Стандартные рекламные карточки заменяются карточками существующих комбо один раз; новые товары и случайные фотографии не создаются. Названия и изображения карточек доступны в прежнем редакторе баннеров.

Заведение получает стабильную метку `merchant_key=dam_alem`, поэтому смена отображаемого названия не исключает его заказы из кабинета. Для существующих заведений метка заполняется при запуске и перед переименованием.

## Telegram

1. Владелец открывает **Настройки → Telegram** в `/partner/dam-alem`.
2. Указывает токен бота и канал `-100…` или `@имя`. Бот должен иметь право публиковать сообщения.
3. При сохранении включённой интеграции сервер проверяет бота, канал и права. Токен зашифрован и не возвращается в API.
4. Кнопка теста отправляет отдельное тестовое сообщение в сохранённый канал. После теста проверьте реальное уведомление о заказе и ссылку на кабинет.

Для кнопки перехода задайте `PUBLIC_FRONTEND_URL` с HTTPS-адресом сайта. Сохраняйте `FOOD_SECRETS_KEY` (или используемый секрет JWT) между деплоями, иначе ранее зашифрованный токен потребуется ввести снова.

Очередь Telegram сохраняется с заказом. Подтверждённые ошибки повторяются с задержкой; неоднозначный тайм-аут требует проверки канала перед ручным повтором, чтобы не дублировать сообщение. Оператор видит ошибки доставки в журнале и может повторить отправку. Сообщение содержит номер, статус и ссылку; подробности заказа доступны после входа в кабинет.

DAM ALEM не изменяет заказ через старые inline-команды Telegram. Они не должны обходить роли оператора/курьера, версии чека и оплату. У старого общего webhook теперь обязательны `TELEGRAM_WEBHOOK_SECRET`, `TELEGRAM_CALLBACK_CHAT_IDS` и `TELEGRAM_CALLBACK_USER_IDS`. Для исходящих уведомлений DAM ALEM этот webhook не нужен.

## Границы проверки

Автоматические проверки используют отдельную SQLite-базу и подменённый Telegram API. Браузерные проверки используют локальную сборку и тестовый API. Они не подтверждают банковский перевод или реальную доставку сообщений в рабочий канал.

Остатки в существующей системе — стоп-лист доступности, не количественный склад. Показатель движения денег не является чистой прибылью: без себестоимости каждого блюда её нельзя рассчитать достоверно. Эти подсистемы не подменены выдуманными расчётами.

Обновлять frontend и backend вместе. Новые поля nullable добавляются штатным механизмом восстановления схемы. До выпуска нужна резервная копия рабочей БД; не следует откатывать только backend после начала записи денежных событий.
