## Три исходные backend-ошибки

### `test_all_legacy_revisions_resolve`

- Смысл: граф Alembic должен иметь одну вершину, сохранять разрешимость старых идентификаторов ревизий и включать ожидаемую историю миграций.
- Причина падения: тест ожидал `m20260927_merge_legacy_heads` и 60 ревизий. Уже существующая `pp20260927_partner_profiles` добавляет следующую ревизию, поэтому фактическая вершина другая, ревизий 61.
- Классификация: устаревшее ожидание, не регрессия этапа 1.
- Production-код: `backend/alembic/versions/pp20260927_partner_profiles.py`, `down_revision=m20260927_merge_legacy_heads`.
- Решение: только тест. Явно проверяются новая вершина, её родитель, 61 ревизия и прежние legacy IDs. Проверки не заменены на безусловное принятие любой вершины.

### `test_upgrade_existing_head_preserves_listing_and_custom_banner`

- Смысл: обновление существующей БД до head должно сохранять объявление и пользовательский баннер; повторный upgrade должен быть безопасен.
- Причина падения: upgrade уже успешно доходил до `pp20260927_partner_profiles`, но тест сравнивал `alembic_version` с предыдущей вершиной.
- Классификация: устаревшее ожидание, не потеря данных и не ошибка миграции.
- Production-код: Alembic env и цепочка существующих миграций недвижимости, баннеров, объединения ветвей и партнёрских страниц.
- Решение: только тест. Обновлено ожидаемое значение версии, дополнительно проверяется наличие `business_showcases`. Проверки исходного объявления, баннера и повторного upgrade сохранены. Миграции запускаются исключительно на временном SQLite-файле.

### `test_courier_api_cannot_self_approve`

- Смысл: обычный пользователь не может одобрить себя курьером, получить административные функции или кабинет курьера.
- Причина падения: тест ожидал 403 для customer JWT на `/logistics/courier/cabinet`. Существующий `_courier_user` требует отдельную сессию `courier_pin_session` и возвращает 401 до проверки полномочий.
- Классификация: устаревшее ожидание после отделения курьерского входа от пользовательского; защита работает.
- Production-код: `backend/routers/logistics.py`, `_courier_user`, `courier_cabinet`, `assert_courier_cabinet_access`.
- Решение: только тест. Проверяются 401, текст требования PIN и отсутствие профиля в ответе. Проверки 403 на административных действиях и запрет доступа заблокированному пользователю сохранены. Успешный отдельный PIN-вход проверяется матрицей доставки.

## Матрица source × fulfillment

**Результат: все 9 сочетаний PASS в полном backend-прогоне.**

Каждая строка проверяет создание → очередь оператора и source-фильтр → запрет пропуска принятия → confirmed → preparing → ready → завершение. Owner detail, overview и counts проверяются на этапах, source и fulfillment должны сохраняться.

- app/site × delivery — API создания → назначение курьера → отдельный PIN-вход → задача у курьера → delivered/done.
- app/site × pickup — API создания → выдача; назначение курьера запрещено, задача доставки не создаётся.
- app/site × dine_in — API создания с пустым адресом → выдача; курьер не требуется.
- operator × delivery — manual quote/create → назначение курьера → delivered/done.
- operator × pickup — manual quote/create → выдача без курьера.
- operator × dine_in — manual quote/create с пустым адресом → выдача без курьера.
- whatsapp × delivery — общий сервис с `source=whatsapp` → назначение курьера → delivered/done.
- whatsapp × pickup — общий сервис с `source=whatsapp` → выдача без курьера.
- whatsapp × dine_in — общий сервис с `source=whatsapp`, пустой адрес → выдача без курьера.

Это проверка WhatsApp source внутри системы, не live WhatsApp intake. Во всех девяти случаях завершение само по себе не подтверждает деньги; оператор не может редактировать закрытую историю, владелец может зафиксировать позднюю оплату.

## Оплата и владелец

`test_dam_stage11_payments.py` проверяет 9 случаев: Kaspi (`kaspi_qr`), Halyk (`halyk_qr`), наличные × completed+unpaid, paid+completed, cancelled+paid/refund.

**Результат: все 9 случаев PASS.**

- Выбор метода не подтверждает деньги; подтверждение денег не меняет статус выполнения.
- Завершённый неоплаченный заказ учитывается в завершённых продажах, но не в поступлениях. Это существующая семантика отчёта, не новая формула.
- Оплаченный завершённый заказ учитывается и в продажах, и в поступлениях своего метода.
- Оплаченная отмена не входит в завершённые продажи; появляется сумма к возврату. Возврат доступен владельцу, оператор получает 403; повторный возврат получает 409. Поступления и возвраты сохраняются отдельно, денежный результат после полного возврата — ноль.
- API владельца проверяются реальными вычислениями на временной БД. Browser-тест отдельно проверяет получение новых снимков через существующий polling 15 секунд, статусы, счётчики и полученные деньги. Browser API контролируемые, это не сквозной тест реального внешнего сервера.

## WhatsApp: фактическое состояние

`services/whatsapp_ai_bot/handler.py` прямо задаёт контракт `Never creates food orders`: распознавание help/menu/category/search/lookup, загрузка каталога, текстовый ответ Cloud API. Есть webhook verification, разбор сообщения и защита от повторов в сессии. Корзины и подтверждения оформления нет.

Для live intake позднее потребуются: диалог корзины/модификаторов, клиент/телефон, отдельный fulfillment и адрес только для доставки, выбор метода оплаты, серверный quote и явное подтверждение; адаптер к общему сервису создания с `source=whatsapp`, устойчивый idempotency по message ID, надёжное хранение состояния/повторов; настройка Meta номера/webhook и backend credentials (`WHATSAPP_*`), затем реальные тесты доставки сообщений и уведомлений статусов. В этом этапе ничего из этого не подключалось.

- Браузерные проверки выполнены в Chrome с контролируемыми API, на ширинах 320/390/768/1440; это не тест физического Android APK, iOS, push в фоне или принтера.

- Startup workers и реальные сторонние сервисы в локальных integrity tests не запускаются.
- Миграции проверяются только на временной SQLite БД; production-схема не изменяется.
