# Конституция проекта Sortirovka24

> Этот документ — «устав» проекта. Он определяет, **зачем** мы существуем, **как** принимаем решения и **чего не делаем**, даже если технически это возможно.

---

## 1. Назначение платформы

Sortirovka24 — **локальная цифровая инфраструктура** микрорайона Сортировка (город Караганда, Республика Казахстан). Мы не стремимся стать универсальным маркетплейсом или соцсетью «для всех». Наша зона ответственности — **повседневные потребности жителей конкретного района** и связь с местным бизнесом, управляющими компаниями и сервисами.

---

## 2. Основные принципы

### 2.1. Локальность прежде масштаба

- Функции должны иметь **понятную пользу для жителя Сортировки**.
- Новый модуль добавляется только если он решает реальную задачу района или его партнёров.
- География, язык и контекст (ЖКХ, автобусы, участковые, местные магазины) — часть продукта, а не «настройка по умолчанию».

### 2.2. Один вход — много сервисов

- Житель регистрируется **один раз** (телефон / Google) и получает доступ ко всем включённым модулям.
- Личный кабинет объединяет заказы, бонусы, роли (мастер, водитель, курьер, партнёр).
- Навигация и дизайн должны ощущаться как **единое приложение**, а не набор ссылок на разные сайты.

### 2.3. Модульность и управляемость

- Каждый крупный блок (еда, такси, объявления и т.д.) — **отдельный модуль** с возможностью включения/выключения через админку.
- Отключённый модуль исчезает из интерфейса **и** блокируется на уровне API (кроме доступа администратора).
- Такси и «Поддержка проекта» управляются отдельными настройками — не через общий переключатель модулей.

### 2.4. Доступность и языки

- Интерфейс обязан поддерживать **русский и казахский** языки.
- Приоритет — мобильные устройства: большинство пользователей заходят с телефона (PWA или APK).
- Тяжёлые страницы загружаются лениво; главная страница — максимально быстрая.

### 2.5. Безопасность и доверие

- Аутентификация жителей — SMS (Mobizon) и/или Google OAuth; сессии — JWT.
- Админ-панель — отдельная JWT-аутентификация с защитой от перебора пароля.
- Секреты (ключи API, FrontPad, Stripe, Telegram) **только на сервере**, никогда во фронтенде.
- Пользовательские данные (телефон, адрес доставки) обрабатываются минимально необходимым объёмом.

### 2.6. Устойчивость к сбоям

- Бэкенд стартует даже при временной недоступности БД; health-check и lazy-init.
- Фронтенд повторяет запросы при сетевых ошибках; не разлогинивает пользователя из-за разового сбоя сети.
- Модули при ошибке инфраструктуры «fail open» (не скрываются случайно), кроме явно выключенных админом.

### 2.7. Прозрачность для команды

- Документация в `docs/` — источник правды о целях и архитектуре.
- Список модулей синхронизирован между `app/backend/services/module_settings.py` и `app/frontend/src/config/modules.ts`.
- Изменения в продакшене сопровождаются проверкой по [PRODUCTION_CHECKLIST.md](../PRODUCTION_CHECKLIST.md).

## 3. Границы проекта (что мы **не** делаем)

| Не делаем | Почему |
|-----------|--------|
| Глобальный маркетплейс без привязки к району | Размывает миссию и ресурсы |
| Хранение платёжных данных карт на своём сервере | Делегируем Stripe / наличные / перевод |
| Публикация контента без модерации там, где это требуется | Жалобы, объявления, мастера — с проверкой |
| Дублирование логики модулей в админке и API | Одна бизнес-логика в `services/`, UI — тонкий слой |
| Breaking changes API без миграции | Alembic + обратная совместимость для мобильных клиентов |

---

## 4. Иерархия решений

При конфликте приоритетов:

1. **Безопасность и законность** (персональные данные, согласия пользователя)
2. **Стабильность продакшена** (не ломать работающих жителей)
3. **Польза для жителя района**
4. **Простота сопровождения** (меньше кода, меньше интеграций)
5. **Скорость разработки новых фич**

## 5. Роли в экосистеме

| Участник | Ожидание от платформы |
|----------|----------------------|
| **Житель** | Быстро найти услугу, заказать еду/такси, подать жалобу, прочитать новости |
| **Мастер / водитель / курьер** | Кабинет с заказами и статусами без лишней бюрократии |
| **Партнёр (магазин, DAM ALEM)** | Заказы, уведомления в Telegram, синхронизация с кассой (FrontPad) |
| **Модератор / администратор** | Полный контроль контента, модулей, статистики, push-рассылок |
| **Разработчик** | Понятная структура repo, env-примеры, документация |

---

## 6. Стандарты качества кода

- **Backend:** FastAPI, async SQLAlchemy, роутеры тонкие, логика в `services/`.
- **Frontend:** React 18, TypeScript, Tailwind, shadcn/ui; переиспользуемые компоненты в `components/`.
- **Именование:** slug модулей на английском (`food`, `gastronom`); UI-тексты — RU/KZ через i18n.
- **Коммиты и PR:** осмысленные сообщения; не коммитить секреты, keystore, `.env`.
- **Тесты:** e2e Playwright для критичных сценариев; backend unit-тесты для account/API.
